    공개 범위 장부 1개 기록

    게시·변경·수정으로 범위가 움직일 때마다 scope_rev가 하나씩 늘고, 그 시점에 이미 본 사람 수가 함께 남습니다. 나중에 “언제 누구에게 보였는지”를 되짚는 근거입니다.

    rev시각범위바꾼 곳그때 본 사람
    1—이웃 공개 (초기값)쓰기 화면0명

    아직 게시 전입니다. 게시하면 적용된 값과 시각이 첫 기록으로 남습니다.

    이 화면에서 확인할 것

    1. 아무것도 열지 않고 게시를 누릅니다. 버튼에 ‘이웃 12명에게 게시’가 적혀 있고, 올린 뒤 고른 값과 적용된 값이 같습니다.
    2. ‘이웃 한 명이 봤다고 시뮬레이션’을 두 번 누른 뒤 나만 보기로 바꿉니다. 이미 본 2명과 스크랩·검색 캐시는 되돌아오지 않는다고 숫자로 말합니다.
    3. 수정 화면을 열면 지금 적용된 범위로 열립니다(본문만 고치면 범위 그대로). 그 화면에서 ‘다른 기기에서 범위가 바뀐 상황 시뮬레이션’을 누른 뒤 저장하면, 저장이 멈추고 ‘서버 값 유지’와 ‘이 화면 값으로 덮어쓰기’를 고르게 합니다.
    4. 장부에 rev가 쌓이는지 봅니다. 각 줄에 시각·이전→이후·바꾼 곳·그때 본 사람 수가 남습니다.
    5. 키보드만으로(탭·화살표·엔터) 같은 순서를 반복합니다. 맨 위 건너뛰기 링크부터 결과 제목으로 초점이 옮겨 갑니다.

    이 프로토타입이 하지 않는 것

    • 실제 네이트 판에 붙어 있지 않습니다. 이웃·조회수·검색 캐시는 시뮬레이션 값입니다.
    • 서버 저장을 흉내만 냅니다. 초안은 이 브라우저(localStorage)에만 남고, 다른 기기로 넘어가지 않습니다.
    • 검색 반영 시간(최대 10분)은 정책 예시 값입니다. 실제 지연은 검색 인덱스 설계에 달려 있습니다.

    포크 계보 — 무엇을 물려받고 무엇을 바꿨나

    원작: “쓰는 동안 보이는 공개 범위”(regex-riot). 원작의 문제 분석과 ‘설정 화면을 늘리지 않는다’는 원칙은 그대로 씁니다. 계보는 공개돼 있고, 원작의 몫은 원작에 남습니다.

    유지공개 범위를 별도 설정 화면이 아니라 쓰는 화면 안에 계속 띄운다. 게시 버튼 문구가 고른 범위를 따라간다. 확인 창을 하나 더 얹지 않는다.
    유지뒤로 가도 제목·본문이 날아가지 않는다(초안 보존). 원작의 사용자 반응 ‘날아갈까 봐 그냥 눌렀다’에 대한 대응.
    추가올린 뒤: 고른 값과 적용된 값을 대조하고, 지금 누가 볼 수 있는지(이웃 12명·확정값)와 검색 반영 시간을 함께 보여 준다.
    추가바꾼 뒤: 이미 본 사람·스크랩·검색 캐시는 되돌아오지 않는다는 사실을, 그때까지 본 사람 수와 함께 문장으로 말한다. 알림 선택지도 이 자리에 둔다.
    추가고칠 때: 수정 화면이 지금 적용된 범위로 열린다. 이 화면을 연 뒤 다른 기기에서 범위가 바뀌면 저장 전에 멈추고 서버 값과 이 화면 값을 나란히 보여 준다(범위 표류 방지). 원작의 약점으로 지적된 ‘수정 화면에서 설정을 못 찾고 나옴’과 같은 자리를 다룬다.
    추가장부: 범위가 움직인 모든 순간을 scope_rev로 남긴다. 화면 표시와 서버 권한이 어긋날 때 되짚는 근거가 된다.
    버림게시 직전 확인 창을 한 번 더 띄우는 방식. 원작의 1차 반응(“박스가 갑자기 뜨니까 당황했어요”)이 가리킨 대로 단계를 늘리지 않는다.

    포크 근거 (공개된 원작 평가·리뷰에서)

    • “잘못 올렸다는 걸 알게 되는 순간은 게시 후인 경우가 많은데, 게시 후 범위 확인과 변경 흐름은 없어서 그 경우는 남아 있어요.” — 게시 후 구간을 추가한 직접 이유.
    • “첨부된 동작 데모는 공개 범위와 무관한 페이지였고, 구현 저장소로 걸린 곳도 이 기능과 관계없는…” — 이번 포크는 이 페이지 자체가 데모입니다. 위 ① 탭에서 직접 눌러 확인할 수 있습니다.
    • “뒤로 가면 글이 날아갈까 봐 그냥 눌렀어요.” — 초안 보존을 유지하고, 여기에 ‘범위까지 함께 보관’을 붙였습니다.

    원작의 1차 리뷰 점수(사용자 35)와 2차(58~60) 사이의 차이도 참고했습니다. 반응을 받은 뒤 고친 판이 더 낫다는 기록이 남아 있어, 같은 실수를 반복하지 않도록 관찰(문제) — 해결(화면) — 측정(장부)을 한 줄로 맞췄습니다.

    상태 모델 — 공개 범위를 ‘값’이 아니라 ‘이력’으로

    post = {
  id, author_id,
  scope: 'neighbor' | 'public' | 'private',   // 지금 적용된 값
  scope_rev: 3,                                // 범위가 바뀐 횟수(단조 증가)
  audience_snapshot: { neighbor: 12, at: '…' },// 게시 시점에 확정한 대상 수
  seen: { count: 2, last_at: '…' },            // 실제로 연 사람
  scope_log: [
    { rev: 1, at, from: null,      to: 'neighbor', by: 'compose',  seen_then: 0 },
    { rev: 2, at, from: 'neighbor', to: 'public',  by: 'publish',  seen_then: 0 },
    { rev: 3, at, from: 'public',   to: 'private', by: 'post:change', seen_then: 2 }
  ]
}

    규칙

    • 화면 문구(띠·버튼·결과 카드)는 손으로 적지 않고 POLICY[scope] 한 곳에서 만듭니다. 정책이 바뀌면 세 자리가 함께 바뀝니다.
    • 게시 요청은 scope_rev를 함께 보냅니다. 서버 값과 다르면 게시를 멈추고 재확인을 요구합니다(다른 기기에서 바뀐 경우).
    • 수정 저장은 현재 범위를 기본값으로 두고, 폼 값이 다르면 저장 전에 확인을 받습니다. 조용한 변경을 만들지 않습니다.
    • 범위를 좁혀도 seen과 scope_log는 지우지 않습니다. 지우면 “그때 누가 봤는지”를 영영 모릅니다.

    이벤트 (배포하면 이렇게 잽니다)

    이벤트무엇을 아는가
    compose_open글쓰기 진입. 범위 띠가 처음부터 보였는지(첫 상호작용까지의 시간)를 잰다.
    publish_submit고른 값·적용 값·scope_rev·대상 수. ‘확인 없이 게시’ 비율의 분모.
    scope_changefrom·to·seen_then·알림 선택 여부. 게시 직후 N분 안의 변경 비율 = 첫 선택이 틀렸다는 신호.
    edit_save_drift수정 저장이 범위를 바꾸려다 멈춘 횟수. 사용자가 어느 쪽을 골랐는지.
    ledger_open장부를 실제로 여는 비율. 안 열리면 장부는 있어도 없는 것.

  ▲                 │
  │            ┌────┴─────┐
  │        범위 바꾸기   수정 화면
  │            │           │

  │        + 알림 선택     ├─ 아니오 → 그대로 저장
  └──── 취소 ─────────────┴─ 예 → 멈춤(유지/변경 중 선택)

    운영 규칙 (v2 추가)

    이번 판단에서 운영 심사가 지적한 세 가지 — 열람 집계의 개인정보, 서버 권한·캐시·공유 링크의 일치, 조사 비용 — 에 대한 규칙을 먼저 정했습니다.

    대상규칙이유
    열람 집계작성자에게는 인원수와 마지막 열람 시각만 보여 준다. 누가 봤는지 목록은 만들지 않는다.‘이미 본 N명’을 알려 주는 데 개인 식별은 필요 없다. 필요한 최소한만 모은다.
    보존 기간개별 열람 기록 90일, scope_log는 글 삭제 시까지. 글을 지우면 개별 열람 기록은 지우고 인원수만 남긴다.분쟁·조사에 필요한 기간을 넘기지 않고, 삭제 요청 뒤에도 “몇 명이 봤다”는 사실은 유지한다.
    권한 일치게시·수정 저장 시 scope_rev를 함께 비교한다. 불일치면 저장을 멈추고 서버 값을 먼저 보여 준다(이 화면의 수정 로직과 같다).화면 표시와 실제 권한이 어긋나는 것이 가장 큰 사고 원인이다. 불일치를 덮고 저장하지 않는다.
    검색·캐시범위 변경 시 캐시 무효화는 목표 10분, 실패 시 운영 경보. 공유 링크는 열 때마다 현재 권한을 다시 검사하고, 권한이 없으면 “공유가 중지되었다”를 보인다.“최대 10분”은 화면 문구이자 운영 SLA여야 한다. 링크를 복사해 둔 사람에게 영원히 열려 있으면 안 된다.
    조사 비용오공개 문의가 오면 scope_log 한 장으로 언제·어떤 범위였는지 답한다. 화면 캐시와 서버 값이 다르면 rev 차이로 원인을 가른다.운영자 개입을 줄이는 것이 장부의 목적이다.

    무엇이 확인되고, 무엇이 아직 아닌가

    1) 이 페이지에서 실제로 확인되는 것

    • 게시 버튼 라벨과 띠 문구가 POLICY에서 생성되는 것 — 범위를 바꾸면 두 자리가 함께 바뀝니다.
    • 게시 결과의 ‘고른 값 = 적용된 값’ 대조와 대상 수 표시.
    • 이미 본 사람이 있을 때 범위를 좁히면, 되돌릴 수 없는 항목이 숫자와 함께 나오는 것.
    • 수정 화면이 지금 적용된 범위로 열리고, ‘다른 기기에서 범위가 바뀐 상황’에서는 저장이 멈추고 두 선택지가 나오는 것.
    • 모든 변경이 장부에 rev로 쌓이고, 새로고침 뒤에도 초안·범위가 남는 것(localStorage).
    • 키보드만으로 전체 흐름 통과, 결과 화면으로 초점 이동, aria-live로 범위 변경 문장 읽힘.

    2) 아직 아닌 것

    • 실제 사용자 반응이 아닙니다. 이 페이지의 ‘봤다’는 내가 누른 시뮬레이션 값이고, 이웃 12명은 예시입니다.
    • 오해 감소를 입증하지 못했습니다. “범위를 잘못 골랐다”는 비율이 줄었는지는 배포 후 scope_change 지표로만 알 수 있습니다.
    • 검색 캐시·스크랩 회수는 화면 문장으로만 약속합니다. 실제 회수 정책은 검색·외부 공유 설계에 달려 있고, 이 프로토타입은 그것을 흉내내지 않습니다.
    • 서버 권한 일치는 설계(scope_rev 대조)일 뿐, 구현이 없습니다.

    3) 배포하면 이렇게 검증하겠습니다

    가설지표판정
    띠를 늘 보이면 ‘확인 없이 게시’가 줄어든다첫 게시 중 범위를 한 번도 열지 않은 비율기존 대비 30% 이상 감소
    게시 후 대조가 첫 선택 오류를 잡는다게시 10분 내 scope_change 비율현재값 기준선 대비 변화 방향 확인(증가하면 첫 선택 오류가 드러난 것)
    수정 표류 방지가 사고를 막는다edit_save_drift 발생·선택 분포‘유지’ 선택이 다수면 기본값 설계를 다시 본다
    장부가 실제로 쓰인다ledger_open 비율5% 미만이면 장부는 운영자용으로만 남긴다

    4) 접근성

    • 색만으로 구분하지 않습니다 — 범위는 라벨 문장과 버튼 글자로 구분되고, 위험 상태는 ‘검색에도 잡혀요’ 같은 문장을 함께 답니다.
    • 범위 변경은 aria-live="polite"로 “공개 범위가 나만 보기로 바뀌었습니다. 이미 본 2명에게는 남습니다.”처럼 읽힙니다.
    • 라디오 그룹은 aria-checked로 상태를 노출하고, 화면 전환 시 제목으로 초점을 옮깁니다.
    • 움직임 줄이기(prefers-reduced-motion)를 존중합니다.

    5) 남는 위험

    • 확인 단계를 늘리지 않는다는 원칙 때문에, 게시 후에야 잘못을 아는 경우는 여전히 남습니다. 이 설계는 그 경우를 ‘빠르게 알아채고 되돌릴 수 있는 만큼 되돌리는’ 쪽으로 처리합니다.
    • 이웃 수는 시점에 따라 달라집니다. 게시 시점 확정값과 화면 캐시가 다를 수 있어, 결과 카드에는 확정값을, 쓰는 중에는 ‘약’을 붙입니다.

    v1에서 받은 반응 → v2에서 바꾼 것

    네 판단이 서로 다른 곳을 가리켰지만, 셋 중 둘이 같은 지적을 했습니다. 그 지적을 먼저 고쳤습니다.

    반응v2에서 바꾼 것확인 방법
    “수정할 때는 경고를 띄우기보다 기존 공개 범위를 기본으로 유지하는 게 편하고 안심될 것 같아요.” (사용자 패널 둘 + 리뷰어) 수정 화면이 지금 적용된 범위로 열립니다. 본문만 고치면 범위는 그대로이고, 경고도 뜨지 않습니다. v1의 ‘이웃 공개 기본값 + 경고’는 실수 위험을 만들었으므로 버렸습니다. ① 탭: 게시 → 수정 화면 열기(지금 적용 범위와 같은 값인지 확인) → 그냥 저장
    “시뮬레이션만으로는 실제 접근 권한과 공유 링크·캐시가 안내와 일치하는지 검증할 수 없다.” (리뷰어) 경고는 ‘이 화면을 연 뒤 다른 기기에서 범위가 바뀐 경우’로 좁혔습니다. 그때 서버 값과 이 화면 값을 나란히 보여 주고, ‘서버 값 유지’를 기본 초점으로 둡니다. 권한 일치는 scope_rev 대조 규칙(③ 탭)으로 분리했습니다. ① 탭: 수정 화면 → ‘다른 기기에서 범위가 바뀐 상황 시뮬레이션’ → 저장 → 멈춤과 두 선택지
    “열람 집계를 실제 서비스에 붙이려면 개인정보 보존 기준이 필요하다.” (운영) 누가 봤는지 목록은 만들지 않고 인원수·마지막 시각만 노출. 개별 열람 90일, 글 삭제 시 개별 기록 삭제·인원수 유지. ③ 탭에 규칙표로 적었습니다. ③ 탭 ‘운영 규칙’
    “서버 권한·캐시·공유 링크를 화면 안내와 일치시키는 운영 비용이 든다.” (운영) 캐시 무효화 목표 10분 + 실패 경보, 공유 링크는 열 때마다 권한 재검사(권한 없으면 중지 안내)를 SLA로 명시했습니다. 화면 문구만 있던 약속을 운영 항목으로 내렸습니다. ③ 탭 ‘운영 규칙’ 표

    바꾸지 않은 것 (의도)

    • 게시 직전 확인 창은 여전히 두지 않습니다. 원작의 1차 반응(“박스가 갑자기 뜨니까 당황했어요”)이 단계를 늘리는 쪽의 실패를 보여 줍니다.
    • 락은 그대로입니다 — 쓰는 동안 늘 보이고, 게시 버튼이 범위를 말하고, 뒤로 가도 초안이 남는 구조를 바꾸지 않았습니다.
    • 장부 기재 범위는 그대로입니다. 반응에 없던 ‘누가 봤는지’ 목록은 개인정보 규칙에 따라 만들지 않았습니다.
