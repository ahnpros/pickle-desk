검색어가 기억 안 날 때 — 단어 대신 맥락으로 찾기

“그거 뭐였지”만 남아도 찾아지게. 언제·어디서·누가·무슨 말투였는지를 입력으로 받고, 왜 이 결과인지 함께 보여 줍니다. 이 페이지의 검색은 실제로 동작합니다.

예시 자료 0건에서 찾습니다
이 조각으로 찾고 있어요 — 빼려면 눌러서 끄세요

이 검색이 하는 일

  • 문장에서 조각을 뽑습니다(명사 후보·숫자·기간 표현).
  • 조각마다 제목·본문·태그에 가중치를 두고 점수를 냅니다.
  • ‘언제’는 감쇠로만 씁니다 — 오래된 것도 순위에서 사라지지 않게.
  • 결과마다 왜 이 결과인지와 맞은 조각을 표시합니다.
※ 예시 자료는 제가 만든 30건입니다. 실제 네이트 검색 로그가 아닙니다.

내 검색 기록

(아직 검색 없음)

왜 ‘검색어를 못 만드는 것’이 문제인가

검색은 단어를 정확히 아는 사람에게 잘 맞춰져 있습니다. 그런데 다시 찾고 싶은 것은 대개 단어가 아니라 장면으로 기억납니다 — “겨울에, 지하철에서, 누가 말했는데, 숫자가 3%대였어”. 이때 사용자는 검색창 앞에서 멈춥니다. 검색을 못 하는 게 아니라 질의를 만들지 못하는 것입니다.

기억에 남는 것지금 검색창이 받는 것이 안이 받는 것
“겨울쯤”, “작년 말”날짜 필터를 따로 열어야 함문장 안의 시간 표현을 읽어 기간 후보로 제안
“기사였는지 판 글이었는지”전체 검색 → 결과가 섞임‘어디서’ 한 번으로 좁힘 + 결과 카드에 출처 표시
“3%대 숫자”“3%”로 검색하면 잡음이 많음숫자·단위를 따로 조각으로 뽑아 본문 매칭에 사용
“누가 말했는지”없음기사·사람 글 구분
미션 경계. ‘읽던 뉴스를 다시 찾는’ 기록 자동 저장(다른 미션)이 아니라, 질의를 만들지 못하는 순간의 입력 방식입니다. 방문 기록이 없어도, 다른 기기에서 봤어도 동작해야 하므로 입력 자체를 바꿉니다.

※ 위 관찰은 일반적인 검색 사용 경험에서 출발한 문제 정의이며, 네이트 사용자 로그로 검증한 수치는 아닙니다. 검증 계획은 ④에 적었습니다.

화면 규칙

  • 결과를 숨기지 않습니다. 상위 5개는 항상 보이고, 점수는 막대와 숫자로 함께 표시(왜 1등인지 확인 가능).
  • 조각 칩은 끄고 켤 수 있습니다. 자동 해석이 틀렸을 때 사용자가 바로 고칠 수 있어야 자동화가 실패해도 검색이 망가지지 않습니다.
  • 시간은 감쇠만. “최근 것만” 같은 강한 필터는 사용자가 고를 때만.
  • 출처(뉴스/판/쪽지/검색기록)를 항상 표시 — 같은 사건이라도 출처가 다르면 신뢰가 다릅니다.

부작용

  • 자동 해석이 틀리면 더 나빠짐 — 조각 칩을 끌 수 있게 하고, 해석을 화면에 그대로 노출.
  • 개인정보 — 쪽지·검색기록은 본인 범위 안에서만. 서버 로그에 질의 원문을 남길 때는 목적·보관 기간을 명시(가능하면 조각만 저장).
  • 연산 비용 — 조각 추출은 질의당 1회, 캐시 가능. 결과 개인화는 넣지 않음(설명 가능성 우선).

지금 확인되는 것 / 확인해야 할 것

이 페이지에서 실제로 확인 가능한 것. 아래 검색창은 예시 자료 30건에 대해 정말로 동작합니다. 문장을 넣으면 조각이 뽑히고, 점수·근거와 함께 결과가 나옵니다. 다만 자료가 30건이라 ‘검색 품질’의 증거가 아니라 동작·설명 가능성의 증거입니다.

검증 설계

  • 실제 로그 1만 건으로 오프라인 평가: 같은 질의에 대해 키워드 검색 vs 조각 검색의 상위 3개 적중률 비교(정답 라벨은 사람 2명이 붙임).
  • 소규모 사용성 테스트 5명: “지난달에 본 글 다시 찾기” 과제로 성공률·소요 시간 측정.
  • A/B: 현행 검색 / 조각 입력. 주 지표 상위3 클릭률, 보조 재검색률.

아직 확인하지 못한 것

  • 한국어 조각 추출의 실제 품질 — 지금 구현은 규칙 기반(공백·2글자 bigram)이고 형태소 분석기가 아닙니다.
  • 자료 30건은 손으로 만든 예시라 실제 문서 분포(길이·중복·표제어)와 다릅니다.
  • 감쇠 계수 0.15는 근거 있는 값이 아니라 조정 가능한 초기값입니다.
  • 네이트 검색의 실제 랭킹·색인 구조 — 확인하지 못해 ‘대체’가 아니라 ‘입력층’ 제안으로 범위를 좁혔습니다.

왜 두 방식을 나란히 재는가

이 검색은 ‘일반 키워드 검색보다 낫다’고 주장하지 않습니다. 대신 같은 질의를 키워드 일치 방식과 조각 방식으로 함께 돌려, 어디서 갈리는지 페이지 안에서 보여 줍니다. 정답 라벨은 제가 붙였고 자료도 제가 쓴 30건이라, 이 표는 성능 주장이 아니라 동작 확인입니다.

  • 조사와 어미가 붙은 문장형 질의에서 두 방식이 어떻게 갈리는지 본다.
  • 0건으로 끝나는 질의가 얼마나 되는지 본다.
  • 결과마다 왜 나왔는지 보이는지 확인한다.

지금 이 자리에서 잰 결과 (라벨 질의 10건 · 자료 30건)

이 숫자의 한계를 먼저 말합니다. 정답 라벨은 제가 붙였고, 자료는 제가 쓴 30건입니다. 실제 네이트 문서 분포(길이·중복·표제어·광고)와 다르며, 표본이 작아 ‘조각 검색이 더 낫다’는 일반 주장의 근거가 아닙니다. 이 표가 보이는 것은 같은 조건에서 두 방식이 어떻게 갈리는지입니다. 자료를 늘린 시험은 바로 아래에서 직접 돌릴 수 있습니다. 실제 로그 1만 건 평가는 아직 못 했습니다.

자료를 늘려서 같은 질의를 다시 재기

정답 문서 30건은 그대로 두고, 같은 주제의 다른 문서 270건을 더해 봅니다. 정답이 다른 문서에 묻히는지 보는 시험입니다.

쪽지와 검색 기록을 넣을 때의 권한과 삭제

항목내용
검색 범위이용자가 볼 수 있는 글만 찾습니다. 남의 비공개 글과 쪽지는 색인에 넣지 않습니다. 쪽지는 보낸 사람과 받은 사람 양쪽이 볼 수 있는 것만입니다.
원본이 지워지면색인에서도 지웁니다. 원본 삭제를 확인한 시점에 색인 항목을 지우고, 검색 결과에 흔적을 남기지 않습니다.
공개 범위가 바뀌면비공개로 바뀐 글은 다음 조회 때 색인에서 빠집니다. 이미 본 검색 기록에는 제목을 남기지 않습니다.
비용색인 갱신은 원본이 바뀔 때만 합니다. 검색은 규칙 기반이라 질의당 모델 호출이 없습니다. 규모가 커지면 색인 크기와 응답 시간이 늘어나는 것이 남는 부담입니다.

바꾸지 않은 것

  • 랭킹 모델을 키우지 않았습니다. 설명 가능성(왜 이 결과인지)을 먼저 지키는 것이 이 안의 주장이므로, 학습 기반 재정렬은 넣지 않았습니다.
  • 개인화를 넣지 않았습니다. 같은 질의에 같은 결과가 나와야 검증·디버깅이 됩니다.
  • 결과 개수를 부풀리지 않았습니다. 관련 없는 문서를 채워 넣지 않고, 없으면 없다고 보여 줍니다.

처음 낸 검색에서 받은 반응과 고친 것

받은 반응바꾼 것
사용자 패널 둘 다 “예시가 30건이라 실제 뉴스나 판에서도 잘 찾을지 궁금하다”정답 문서 30건은 그대로 두고 같은 주제의 다른 문서 270건을 더해 같은 질의 10건을 다시 채점하는 버튼을 넣었습니다. 방금 돌린 결과는 조각 검색 hit@1 10/10, hit@3 10/10, 0건 0입니다. 늘어난 자료도 제가 만든 것이라는 점은 그 자리에 적었습니다. [다섯째 탭]
리뷰어 “형태소 정리와 필드 가중치에 기반한 단어 매칭이고, 30건과 라벨 10건만으로는 키워드 검색보다 낫다고 판단하기 어렵다”이 검색이 단어 매칭이라는 점을 먼저 적었습니다. 같은 자료에서 키워드 방식과 나란히 채점하고, 300건에서도 두 방식을 함께 돌립니다. 조각 검색이 더 낫다는 일반 주장은 하지 않습니다.
운영감사 “실제 색인 규모의 응답 속도와 품질, 쪽지와 검색 기록 연동 시 접근 권한과 삭제 동기화 부담”300건에서 질의 10건을 두 방식으로 돌린 합계 시간을 화면에 표시합니다. 방금 값은 114ms였습니다. 쪽지와 검색 기록의 접근 범위와 원본 삭제 시 색인 삭제, 공개 범위 변경 시 색인 제외 규칙을 다섯째 탭 표에 적었습니다. [다섯째 탭]

바꾸지 않은 것

  • 학습 기반 재정렬을 넣지 않았습니다. 왜 나왔는지 보이는 것이 이 안의 중심입니다.
  • 300건을 실제 색인이라고 쓰지 않았습니다. 제가 만든 문서로 정답이 묻히는지만 보는 시험입니다.
  • 쪽지와 검색 기록 검색을 켜 두지 않았습니다. 예시 자료 안에서만 동작하고, 실제 연동은 권한 규칙만 적었습니다.

이번 라운드에서 받은 반응과 바꾼 것

사용자 패널 둘, 리뷰어, 운영감사가 남긴 문장과 그에 대응해 이번에 더한 것이에요. 리뷰어가 이번 라운드 개선점이 분명하지 않다고 했으니, 바꾼 것과 바꾸지 않은 것을 나눠 적었습니다.

받은 반응바꾼 것
일반 사용자와 파워유저 “자체 자료 말고 실제 기사에서도 얼마나 잘 찾는지 궁금해요” 내 문서로 확인 상자를 넣었어요. 기사 제목과 본문을 붙여 넣고 같은 질의를 넣으면, 같은 가중치로 점수와 맞은 조각을 계산해 보여 줘요. 다만 붙여 넣은 문서는 이 상자 안에서만 쓰고 페이지 색인에는 넣지 않아요.
리뷰어 “이번 라운드에서 무엇을 개선했는지 불분명하고, 300건으로 늘려도 실제 질의에서 키워드 검색보다 나은지 판단하기 어렵다” 이 표가 이번에 바꾼 것이에요. 성능 우위 주장은 하지 않아요. 같은 자료에서 두 방식이 갈리는 지점을 보여 주는 데까지만 갔습니다.
